# Why A, T and C never engaged in gap a, the fixes, and the rerun (11-05)

## 1. Diagnosis

### The common cause: the yardstick read every tail24 / long40 prompt in 1024-token chunks

The gate's yardstick (`basalt_rules.py pfy`, line 333 `qq.engine_args(...)`) starts the engine with quant_quality's
fixed args (`strata-r22p022n/tools/quant_quality.py:38`: `--expert-cache 1`). A one-slot cache can lend nothing
(`fits_one`: a loan must leave 128 slots), so the auto scan returns 0 and
`src/program/generate.cpp:10512` sets `o.prefill_chunk = 1024; // nothing lendable: small buffers of its own` for any
`--prefill auto[:N]`. The plan's "tail24 at the served chunk, `--prefill auto:16384`" (GATE-PLAN A3) therefore ran at
1024; its note "bare auto = 8192 in the yardstick" was wrong too. Evidence:
- gap 17's yardstick run p210hcr printed `strata prefill: chunk 1024 tokens: STRATA_PF_HC_REGION on`;
- every pfy stderr lacks the `prompt chunk auto:` line and says "the prompt path allocates its own buffers";
- speed: ~1,100 tok/s at every length (904 chunk passes x ~0.9 s ~ the 820 s per tail24 run), against 4,093 tok/s in
  the gap's own server profile at chunk 16384;
- with the served share kept (B16s, A16s, cpushare16) 1,220 MiB more VRAM was free (8,501 vs 7,281) = 480 ring slots
  x 2.66 MB, and no "fused int8 kernels" line: the 1024 layout was itself a staged layout.

tail24's rests (after removing the last token: 299-999, two of 255) are the same after 1024 as after 16384 (16384 =
16 x 1024), so each prompt still ended in one staged rest, which is why A16 did run.

### A (STRATA_PF_AHEAD=1): it fired without the share. With the served share the layout had no slots to copy into

- A16 (share 0): stream-all from 1024 (`prefill.cpp:263-266` at 3383d1f8d), so the 1024 layout is stream-all:
  `ring_slots` = 512 (`:426`), `ring_room_at = stage_slots(T)` = 512 (`:2158-2161`), ahead_n = min(112, (512-32)/2).
  24/24 prompts copied ahead (4,685-5,264 each, 96-98 % read in place). Identical to B16.
- A16s (share 0.4, `_MAX` 1792): arming the share sets the stream-all size to 1792 (`:3012`
  `g_stream_min_share = cpu_share_max()`). 1024 < 1792, so `ring_slots(1024)` = STAGE, `stage_slots` = STAGE_GRP = 32,
  and `ahead_room > STAGE_GRP` (`:4074-4077`) is false: ahead_n = 0, nothing copied, and the line (`:6490`, printed only
  when something was copied) never came. UNEXERCISED, not wrong.
- Basalt's original (31aacda2) grows a staged layout's ring by 2 x min(64, T/32) slots out of the loan. That is our mode
  2 (rounding-level through the share). Mode 1 copies only into slots the layout already holds, which is what makes it
  exact. At the served chunk (16384 + a staged rest, share 0.4) the layout is stream-all (512 ring) with or without the
  share, so A does fire there. The test just never ran at that chunk.
- Our setup, otherwise: no peer prompt path (the 4060 Ti `--expert-cache-device1 3300` is a decode helper; `!m.pp`
  held in A16). In the SERVED config `--kv-resident 32768` makes every QSA layer `kv_mode == 1` for every prompt
  (`core/layer.cpp:753`), so `copy_ahead` skips the 12 QSA layers (`:4116`, Basalt's rule). The yardstick drops
  `--kv-resident`, so it copies for all 48. The server's per-request relayout gives a short prompt (< 1792) a staged
  layout, so mode 1 only acts on the rests of prompts longer than 16384.

### T (STRATA_PF_TAIL_SPLIT=1): the rule cannot hold at a 1024 chunk; at 16384 it worked

- `prefill.cpp:3421-3424` needs both halves of C + rest to be at least the stream-all size. At C = 1024 = stream-all,
  1024 + rest < 2048, so it never holds: 0 lines. With the share, C = 1024 < 1792 makes `m.ring = STAGE`, so `own_plan`
  (`:3406`) is false.
- The same gap's server profile (chunk 16384) shows it working: Tp-pp16k "16669 ... chunks of 8448 and 8221",
  Tp-pp64k "... 8960 and 8498", the 16384 checkpoint moved to the end, GPU timeline 4,099 -> 3,799 ms (pp16k).
- A second, hidden miss: `basalt_rules.py expect_plan` uses `tokens`, but the yardstick reads tokens - 1 in a batch (the
  last token goes through the first window; the cuts in `generate.cpp:17656` end at n - 1). Cuts 16640 and 49408 leave
  255 < 256, so even at 16384 the rule would have expected 24 lines and got 22.
- Gap a's T KL "PASS" (KL 0) only shows that T16 = B16 bit for bit, because T never fired. The tail24 references were at
  1024 too (cpushare16 had no stream-all chunk at all).

### C (STRATA_PF_FIRST_CHUNK=1): auto:24576 is auto:16384

- `generate.cpp:3475`: `prefill_auto_max = N >= 32768 ? 32768 : N >= 16384 ? 16384 : 8192`. The scan's ceiling for
  auto:24576 was 16384, so the lend gave "16384 tokens, a 512-slot ring, 3231 slots" (c_lend FAIL), and the switch needs
  C > 16384 (`prefill.cpp:3409`). Behind that: the yardstick's C16 / C40 at `auto:N` would have read at 1024 anyway.
- Basalt's original (e8f3b84b) runs under Basalt's own bare-auto ceiling, 32768 for blobs > 1.5 MB (ours: 2.66 MB), and
  also needs prompts >= 2 x 16384. Ours plans any prompt > C whose rest is not one staged chunk (`:3412`), a superset.
- The 5080's cache is 4,585 slots. A 90 % loan with a full 512 ring allows about 20-22K at auto:32768 (estimate; to be
  measured).
- STRATA_DEFAULTS=026 does not touch any of the three (it keeps layer-major off, and the config pins
  `PREFILL_LAYER_MAJOR=0` anyway).

## 2. Fixes: three commits on r23-basalt-prompt (KarlGrier, not pushed)

None of them changes what the switches compute: the same slots, chunks and plan lines. With every r23 switch unset,
nothing new runs or prints. Each commit adds the rule as a pure function, with the reason it does not apply, in the new
header `include/strata/prefill/r23_plan.hpp`, adds a "not applied" line, and adds checks to the new CPU test
`tests/prefill/r23_plan_test.cpp` (in CMake).
- **60418ad11 (A):** `r23::ahead_slots`. Every prompt with a staged chunk now prints a line: the old one plus the layout
  and slots, or "0 experts copied ahead ...: <reason>". Every layout prints "r23 switches: a layout for C-token chunks
  (stream-all from S, N staging slots, an R-slot ring)" when any r23 switch is set.
- **750d5caa2 (T):** `r23::tail_split`, and `own_plan_why` names why a run does not plan its own chunks. A staged rest that
  is not split prints "STRATA_PF_TAIL_SPLIT not applied: ... the halves would be A and B: <reason>".
- **b8128327d (C):** `r23::first_chunk`. When the chunk is not above the first chunk, `Prefill::init` says so once and
  names auto:N's rounding. A multi-chunk prompt it does not plan prints "STRATA_PF_FIRST_CHUNK not applied: ...".
- The "not applied" lines have no colon right after the name, so plan-line counts are unchanged. `generate.cpp`'s auto:N
  rule and the 1024 fallback are upstream's and stay. The fixes on the test side are in the rerun's rules (section 5).

## 5. The rerun: `work/r23/gap-basalt-fix.sh` + `work/r23/basalt_fix_rules.py` (written, NOT run, no .ready)

Conventions follow gap a: `set -u -o pipefail`, `exec 8>&- 9>&-`, preflight, exits 0 / 1 / 3 / 4, port_gap4
begin/end, kcheck after every arm, env checks by /proc/PID/exe, deadline `GF_MAX_MIN` (default 190).

Pre-gap refusals: `buildcheck` (SHA256, SOURCE at b8128327d, GATES, TESTS all PASS) and the rules' selftest.

Arm configs are written to `gap-fix/configs/`, never to gap-configs/, which gap b uses. The rules reuse basalt_rules.py
read-only.

Steps:
1. BASELINE: exact7 B vs g17-p210a, and B40 vs p210.
2. A: B16 / A16 / B16s / A16s at an explicit `--prefill 16384`, then exact7 A.
3. T (Karl 11-05: long40 at 16384 too):
   - tail24: unfused16 and T16;
   - long40 at an explicit `--prefill 16384`, fp16: B40_16, unfused40_16 (B + PF_FUSED=0), cpushare40_16 (B + the
     served share) and T40_16;
   - the KL rule: tail24 T16 vs B16 / unfused16 / cpushare16, and long40 T40_16 vs B40_16 / unfused40_16 /
     cpushare40_16.
   The bare-auto T40 is dropped: it read at 1024, where T cannot fire, so its KL half was vacuous. At 16384 T fires on
   1 of long40's 40 prompts (tf-long64k-17408 -> 8704 + 8703); the other 39 check that nothing else moved.
4. C: the stack (gap a's S_PARTS + this gap's A / T where they passed), one scan start at `auto:32768` giving N, then
   C16 / C40 at an explicit `--prefill N`, the VRAM check and the KL rule. C starts only if the scan, C16, C40 and the
   close fit before the deadline.
   C40 is judged against step T's 16384 long40 references (B40_16, unfused40_16, cpushare40_16; Karl 11-05: "yes, use
   the 16384 references"). If those were skipped by the deadline, C's long40 part is NOT DECIDED; it is never judged
   against the 1024 ones. The comparison against gap 8's 1024-chunk references is reported beside it as an INFO line
   (gates `*_Cinfo1024_long40`) and never decides ("report the 1024 comparison beside it as information only"). The
   selftest checks a case where the two disagree: the decision follows the 16384 one.

The decision rules are gap a's:
- Exact: exact7 and byte-identical logits.
- Rounding-level: kernel_rule2 + 3 (`kl --mode new`: the point NLL is INFO; the many-positions bound is revoked).
- "Exercised" evidence is required, otherwise NOT DECIDED:
  - A: `ahead` M > 0 in both A arms, and `chunk` = 16384 from the layout lines (for B16 / B16s, from their args).
  - T: plan lines equal to the formula on n = tokens - 1, on T16 (22 of 24) AND on T40_16 (1 of 40), and `chunk` =
    16384 for T16, T40_16, B16 and B40_16.
  - C: c_lend N > 16384, plan_C16 = the formula at N, chunk_C16 = N, and vram_C.

Output: `gap-fix/decision-fix.txt`. Deadline `GF_MAX_MIN` 190 (Karl 11-05). Time with 8080 down is about 1.6-2.0 h:
open 3, baseline 14, A 28-36, T 32-48 (2 tail24 + 4 long40 runs at 16384), C 14-16, close 3.
