Exact BF16 exponent compression is the actual new experiment. It can be lossless if decoding reconstructs every original BF16 bit pattern.

- Effects on coalesced memory access.

6. Commit-time admission: repeat, with a hidden implementation cost
This is already in your Opus plan as committed-versus-speculative weighting.

The roughly 20% discarded-row calculation is plausible. It is not evidence that 20% of admissions are harmful:

The proposal also combines two different modifications:

7. Exact zero skipping: genuine premise, incomplete correctness and performance arguments
This is worth a cheap probe. The response unnecessarily leaves its main premise unresolved:
- Upstream CPU IQ4_NL down projection uses Q8_0 intermediates.
- The GPU native path uses Q8_1 intermediates.
Thus exact zero activation codes can exist in the computation already being performed. Sources: CPU native experts, GPU kernels

But three problems need fixing.
A. Its arithmetic argument does not prove bit identity
The response proposes summing 32 integer products and then applying scales.

The actual CPU kernel forms multiple integer partials, accumulates them through eight FP32 FMA lanes across blocks, then performs a horizontal reduction. Collapsing each block into one integer total changes the surrounding floating-point evaluation order.

A carefully designed implementation could preserve the existing reduction structure. Otherwise this is a rounding-level candidate, not an already-proved bit-identical transformation. Source: IQ4_NL multi-token kernel
B. Twenty percent zeros need not eliminate twenty percent of reads
Scattered zeros can share packed bytes and cache lines with nonzero weights. Skipping arithmetic does not necessarily avoid those memory transactions.

A column-oriented layout might help, but it must retain the original scale associations and avoid losing coalescing.

There is also multi-token reuse: if several tokens share an expert, a column can be omitted entirely only when it is zero for all those tokens. Under an illustrative independence assumption, 20% per-token zeros becomes 4% jointly zero for two tokens and 0.8% for three. Your remaining CPU work is mostly singleton, which helps this particular opportunity, but the actual grouping must be measured.
C. Zero block scales do not identify dead hidden units
One zero IQ4_NL scale zeroes a block of weights in one output row. It does not establish that an entire hidden unit is dead.

Even a hidden unit with a completely zero outgoing column can affect the activation quantizer’s block maximum. Removing it before quantization can change the scale—and therefore the codes—of neighboring live units.

Corrected cheap test: sample the actual CPU/GPU quantized intermediate buffers, grouped by expert and width. Count jointly zero coordinates, complete zero blocks and runs large enough to eliminate real transactions. Separately test complete outgoing columns or provably zero-producing rows for static elimination.

Gain assessment: “20% zeros therefore +3–6%” is not supported. As an illustrative CPU-only model, actually eliminating 20% of down-projection bytes—about 41% of aggregate expert bytes—would yield roughly 3.4% whole-window improvement if that CPU work were perfectly bandwidth-proportional, before overhead. That makes the opportunity interesting, but the difficult step is eliminating bytes, not finding zero codes.
8. Partial-sum runahead: plausible, but its proposed evidence is insufficient
This can preserve target computation if the partial result is used only to predict prefetch destinations, and all speculative GDN/attention/PLE state is isolated and discarded. Actual routing and expert execution must still use the complete result.

The OD-MoE comparison does not establish its accuracy. A complete quantized shadow model is a different perturbation from deleting the CPU tier’s entire contribution.

The suggested 85–90% overall top-10 overlap is also the wrong gate. Approximately 85% of routed entries are already served from your GPU caches. A predictor can look accurate while providing little information about the experts that matter.

Measure instead:
- Precision and recall on nonresident experts.
- Transfers completed before actual demand.
- CPU and transfer time avoided.
- Shadow execution cost, wrong transfers and extra contention.
The basic top-30 routing trace cannot support the proposed offline ablation. Recomputing next-layer routing with contributions removed needs activations, per-tier weighted contributions and the relevant next-layer state.

Finally, the shadow computation consumes part of the supposed 180 μs lead time. And starting copies during CPU work can recreate the DRAM contention that hurt your earlier warming experiment.

Verdict: a legitimate ambitious predictor experiment, but substantially more work than the response implies. +2–6% remains an unpriced hypothesis.

The proposed diagnostics and “enablers” also need tightening
Underclocking is useful, but not a clean yes/no classifier
The DDR, GPU-memory and PCIe experiments are reasonable sensitivity tests. “Thirty minutes each” and their binary interpretation are optimistic.

DDR changes can alter timings and controller behavior. GPU memory changes can alter core clocks through power limits. Reducing PCIe bandwidth can change your adaptive share and admission history.

Use fixed work, record actual clocks and policy changes, and inspect component timing. A flat response to one knob does not prove the corresponding resource is irrelevant.
Alternating every 16 windows does not guarantee 1% resolution
Adjacent windows differ in width, routes, cache contents and accepted length. Adaptation also carries state from one treatment into the next. Some switches are read once or incorporated into captured graphs.

For kernel comparisons, replay identical inputs. For cache policies, restore or independently evolve policy state and counterbalance runs. Measure the uncertainty; do not promise it from the switching interval.
Identical CPU/GPU kernels would be a substantial project
The existing backends do not merely differ in instruction scheduling: activation formats and reduction structures differ too. Matching expert kernels alone would not fix differences in final accumulation, state handling or RNG behavior.

The Gumbel-coupling reference is real and useful: it can produce drafter-invariant seeded outputs for an unchanged target distribution with correctly shared randomness. But replacing the production verifier with that sampler cannot validate the production accept/residual logic it replaced. It also cannot hide target-logit differences caused by state bugs or arithmetic. arxiv.org
