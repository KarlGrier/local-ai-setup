### Why each matters on this specific topology

The 5080 runs at PCIe Gen5 ×16 (57.8 GB/s H2D) directly off the CPU root complex; the 4060 Ti runs at Gen4 ×4 through the chipset (6.4 GB/s H2D) sharing bandwidth with an NVMe SSD [3906]. *[⚠ only partly supported by the cited source: Link/speed supported; CPU root complex and NVMe sharing not stated.]* The cost model in PCIE_BALANCE must weight these 9×-different lane speeds correctly: sending one 2.18 MB expert over the chipset ×4 takes ~0.34 ms (2.18 MB / 6.4 GB/s), versus ~0.038 ms over Gen5 ×16. At T = 1, where the CPU pool per layer is 140 µs and the GPU phase 72.5 µs [1339][3906], even a single mis-allocated expert on the chipset link can expose 0.3 ms of serial PCIe wait inside a 12.5 ms T1 window [1338]. PCIE_MIN1 ensures the lane is at least claimed when it would otherwise idle. *[⚠ only partly supported by the cited source: Per-layer timings and T1 window supported; 0.3 ms single-expert wait not stated.]*

### The n_stages caveat

The `pipeline_windows` field is a single integer (the number of decode windows pipelined concurrently) [1338]. At `n_stages == 1` the pipeline is degenerate—there is no overlap, and the GDN snapshot machinery adds memory pressure without speed benefit. Meaningful overlap requires n_stages ≥ 2, which doubles the peak GDN-state footprint (72 MB for 36 layers × 2 snapshots [2293]) and forces a state-checkpoint/replay decision at each window boundary. No source in the evidence documents an n_stages > 1 implementation in v0.2.6, so the caveat is structural: the switch name implies the capability but the implementation may not yet engage the second stage on a two-card layer split.

### Qwen4 carryover: the pipeline-snap flag

Pipeline-snap overlap is the single most Qwen4-Flash-relevant Tier 0 item. Qwen3.8-Flash-Next and the incoming Qwen4 architecture carry 36 GDN layers whose "fixed-size recurrent state" [1892][2297] must be rolled back to the window start whenever an MTP draft is rejected. The user's served MTP runs up to 7 draft tokens with the adaptive draft-length rule [user_setup], so a rejected draft at position 3 of 7 forces rollback across all 36 GDN state matrices. The per-token GDN state is "2 MB" of 32 matrices of 128×128 floats at FP32 [2297]; at FP16 per layer it is 1 MB [2293]. A pipelined decode that snapshots at window boundaries rather than per token avoids the 36 MB-per-token cost and lets the 5080 begin the next window's GDN recurrence while the current window's MTP verification still completes—hiding up to 1.98 ms of inter-window latency where the GPU is already idle 0.42 ms [3]. The carryover is stronger for Qwen4 because its 51B PLE table sits at layer 2 [1892][2247], giving only a ~0.27 ms prefetch window [2607 equivalent in findings], so every microsecond of GDN state rollback that is hidden by pipelining directly feeds into the table-read overlap budget.

## Tier 1: PLE / n-gram table optimizations — highest leverage, 100% output-exact by construction

### Losslessness ground

Every PLE-path improvement below is output-exact by construction because PLE row indices are derived solely from input token IDs via a deterministic multiplicative-XOR hash, never from hidden states [2611][2767][2606]. The Engram paper states this as a design choice: "Unlike MoE which relies on runtime hidden states for dynamic routing, Engram employs a deterministic retrieval mechanism based solely on input token IDs, naturally decoupling parameter storage from computation" [2611]. Strata's own comment confirms that OS read hints cannot alter gathered values: "Ask the OS for the next window's pages in one go (PrefetchVirtualMemory / MADV_WILLNEED, a hint that cannot change a value: an unfetched page is faulted by the read)" [2851, line 587-588]. The unsloth llama.cpp batched-readahead patch (PR #137, a different program from Strata) reports "byte identical on both qwen4exp and gemma4" output after the patch [2613]. No reordering, page-hinting, cache-size change, or batching of reads can alter a row's bytes, because the row content is a pure function of the token sequence.

### Current state and the hit-rate gap

The user's Qwen3.8-Flash-Next PLE table is IQ4_NL, 26.82 GB, 320 M rows of 90 B each (row_bytes for IQ4_NL per [2849]), read at layer 1 (second decoder block) [2481][2607]. Strata v0.2.6's default row cache is `cache_rows = 1u << 20` = 1,048,576 rows × 90 B ≈ 95 MB [2849]. The NOTES.md records "row-cache hits 43%" on decode windows [2576]. SlackTier (a separate SGLang plugin, not Strata) measures the same class of n-gram lookup: a 1M-row LRU hits 74% of agent decode lookups, 5M rows hit 81-85%, and 5% of the table (16M rows) hits 86-89% [2607]. For chat workloads the ceiling is lower (35% at 1M, 42-47% above 5M) [2607]. The 43%→74-89% gap is therefore a cache-size and eviction-policy gap, not a structural one.

### Five concrete improvements

**(1) Bump `--ple-row-cache` from 1 M to 8-32 M rows.** At 90 B/row, 8 M rows = 720 MB and 32 M rows = 2.88 GB [2849]. The user has 96 GB DDR5; the Strata server occupies 50-63 GB [user_setup], leaving 33-46 GB free. Even 32 M rows (2.88 GB) is well inside that headroom. SlackTier's data predicts the 1M→5M step alone lifts agent-decode hit rate from 74% to 81-85% [2607]. Strata's 43% is below even the 1M-row peer benchmark, suggesting the user's workload mix (chat-heavy, short sessions) sits in the lower SlackTier regime; still, 8-32 M rows should lift hit rate into the 70-85% band. The set-associative row cache in v0.2.6 (8 ways per set, round-robin within a set) [2849] bounds eviction cost at O(WAYS) per insert and never grows past `sets × WAYS × row_bytes`, so the bump is a pure RAM-for-latency trade with no code change.

**(2) Apply `MADV_RANDOM` + batched `MADV_WILLNEED` hints on the PLE shard in mmap mode.** The unsloth llama.cpp PR #137 (a different engine, not Strata) shows that `MADV_RANDOM` alone is *3.7× slower* than leaving the mapping alone (130,112 vs 34,767 ns/gather), because "Readahead was pulling 128 KB per fault and the Zipfian reuse was hitting it" [2613]. The fix is `MADV_RANDOM` plus batched `MADV_WILLNEED` four steps ahead: 4,666 ns/gather, a 27.9× improvement over bare `MADV_RANDOM` [2613]. Strata v0.2.6's Direct mode uses unbuffered 4 KiB preads and does not use mmap, so this patch does not apply directly [2849]. However, v0.2.6's mmap path (`--ple-io mmap`) already implements a window-ahead hint via `PrefetchVirtualMemory`/`MADV_WILLNEED` [2851, lines 587-589]. The user should A/B `--ple-io mmap` with `STRATA_PLE_AUTO_MMAP=1` against the default Direct mode on a cold 32 K prompt. NOTES.md's mmapwarm probe (whole 28.8 GB table in page cache) gives only ≤1.6% prompt improvement and no decode gain [2576], which caps the benefit: the remaining 2 s at 32 K is "the per-token layer-1 PLE loop (ple_block + history advance launched once per token, prefill.cpp:360-373) + hashing/gather", not I/O [2576].

**(3) Unblock `PleTable::gather_batch` while a per-token read is in flight.** In v0.2.6's `ngram.cpp`, line 540: "if (impl_->pending) { err = "PleTable::gather_batch while a token is in flight"; return false; }" [2851]. During speculative decode, `verify.cpp` issues per-token `prefetch_rows` calls as MTP drafts tokens [2854, lines 2900-2906], then calls `gather_batch` for the whole window at line 2917 [2854]. If even one per-token prefetch ticket is still outstanding, the batch gather is rejected and the window stalls. The fix is a scheduling change in `ngram.cpp`: before rejecting, drain any completed prefetch tickets or block briefly on the outstanding one (the p50 read is ~450 µs in decode, ~110 µs in prompts [2576]), then proceed. NOTES.md measured that moving the PLE gather "beside layer 0" on a separate thread produced "−2.7 % T4, T1 = (measured)" net [2576], but a targeted unblock in `gather_batch` avoids the thread-creation overhead and keeps the existing `early_ple_flag_mode` path [2854, line 2914].

**(4) Port v0.2.13's `kStackMisses = 64` fast path.** In v0.2.13's `ple_reader.cpp` (a *later version than the user's v0.2.6*): "constexpr size_t kStackMisses = 64; if (n <= kStackMisses)" routes small batches through a stack-allocated `Miss misses[kStackMisses]` array, sorted by page offset, with no `unordered_map<uint64_t, size_t> by_page` or heap `std::vector<Job> jobs` [2848][2858]. The v0.2.6 `issue()` always allocates the hash map and job vector [2858]. A decode window's per-token prefetch is exactly 16 rows (PLE_N_HEADS = 16) [2856][2862], and the MTP draft loop prefetches up to 7 draft tokens one at a time, each a 16-row ticket [2855]. Even a batch of 4 tokens (64 rows) fits the stack path. The general path's hash-map insert + vector push for 16 rows costs 200-400 ns more than the stack sort [2848 comment: "the sort of every miss loses to the hash there when many rows share a page, so the stack path is kept to the size it wins at"]. This is a ~100-line backport with no output change: it only changes *how* the same rows are queued.

**(5) SlackTier's layer-first issue order and per-layer cache split.** For the user's Qwen, there is one PLE table at layer 1, so layer-first ordering is structurally trivial (only one table to issue) [2607][2481]. This item carries over to the DeepSeek-V4.1-Flash-1017 setup, which has *two* Engram layers whose prefetch windows differ by 30× (0.3 ms vs 9.3 ms) [2607]. SlackTier's per-layer cache model puts f ≈ 0.8 of the cache budget on the small-window layer (layer 1) and the remainder on the large-window layer (layer 14), and "the curve is flat: Layer-1 shares from 0.25 to 1 differ by a few tenths of a millisecond" [2607]. On the user's 96 GB RAM, a 1 GB cache split 800 MB / 200 MB between the two V4.1 Engram tables would cut the small-layer overhead from 4.9% to 1.3% [2607]. This requires a code change in Strata's cache allocator (currently a single global row-cache), so it is a Tier-1 item for V4.1 but a no-op for Qwen.

### Companion: issue #2622 and the `--ple-inflight` / `--ple-io` sweep

Issue #2622 (reported 2026-10-15, commit 36381540f9, merged into v0.2.6) fixes a redundant-request bug: the old code matched prefetched keys by position, so prefetching A,B,C,D,E,F then gathering D,E,F,A,B,C reissued 96 rows even though every 16-row vector was already prefetched [2853]. ### Qwen4-Flash carryover

The Qwen4 PLE table (51.2 B parameters, IQ4_NL) sits at layer 2 (the smallest prefetch window: 0.27 ms at layer 1 per [2607], and "about 56μs" for a layer-2 Engram module under CXL-style pooling [2606]). Because the table is read *before* most layers run, every millisecond of gather latency is fully exposed. The 43%→74-85% cache bump and the stack-path fast path (item 4) directly shrink that exposure. The Engram paper's CXL experiment confirms that "the compute intensity of early dense blocks provides a sufficient temporal window to mask the retrieval latency" only when the table is already in fast RAM; at 0.27 ms the window is "a stringent requirement" [2607][2606]. On the user's 96 GB rig, pinning 32 M PLE rows (2.88 GB) in the set-associative cache [2849] plus the 68 GB expert store [user_setup] keeps total RSS under 80 GB, well within the DDR5 ceiling.

## Tier 2: Expert-cache policy changes — exact-size slots, score-based eviction, inter-layer affinity, fine-grained transfer

All four changes below preserve output bit-for-bit: they alter *which* experts sit in a cache slot or *how* their weight bytes reach the GPU, never the arithmetic of the expert itself. PLE row indices derive from token IDs only, and expert GEMM inputs are unchanged by any of these scheduling moves, so no logit is affected.

### Score-based eviction replacing LRU

HybriMoE's Minus-Recent-Score (MRS) policy replaces recency with accumulated routing scores: only the top *p* expert scores are summed, where *p* = 2 × activated-experts, exploiting the observation that "the reuse probability of experts with lower scores does not exhibit significant differences" [325]. At 25 % cache capacity MRS beats LRU by 6–8 % across Mixtral, DeepSeek, and Qwen2 [325]. The llama.cpp expert-cache RFC independently confirms the skew that makes score-based retention effective: "On Qwen3.5-122B, the top 10% of experts take ~80% of hits" with "Gini ≈ 0.76, ~99% simulated hit rate at 69% expert budget" [501][423]. FreeToken's replay study shows that even plain LRU beats static prefill-chosen placement by 25–47 pp in miss rate (16 % vs 41 % vs 62 % at 37 % / 11 % pool capacity), so moving from static to LRU is already large; MRS adds the remaining 6–8 pp on top [240]. Importantly, the llama.cpp RFC's own decode traces found "Plain recency already catches it" and that "a predictive prefetch tier came in the worst, not the best" at hit@32 ≈ 0.66 [501]. This tempers expectations: MRS helps most at *low* capacity (≤30 % of pool), which is exactly the regime on this rig where 7,900 of 25,000+ Qwen experts are cached. For Qwen4-Flash's 512 routed + 1 shared, top-10 routing, the activated-per-token set is wider and the score distribution flatter, so the MRS advantage over recency narrows but the absolute hit-rate gap to LRU remains [325].

Note: `STRATA_ROUTE_PRIOR` in the v0.2.6 port biases *which experts run* and is "lossy by design (changes which experts run)" [2]. The MRS / ExpertFlow policies discussed here change only *which cached experts are evicted*; the router still selects freely, so the output is exact **[Consistency check: contradicts "ExpertFlow / Prefetch-Steered Routing (STRATA_ROUTE_PRIOR) | 92% cache hit (ExpertFlow context) | "lossy by design (c..." elsewhere in this report; not settled (The report conflates a pure cache-eviction policy with STRATA_ROUTE_PRIOR/Prefetch-Steered Routing, which is explicitly lossy because it changes routing decisions.)]**.

### Inter-layer expert affinity as a retention prior

ExFlow proves that "pre-trained GPT MoE models implicitly exhibit a strong inter-layer expert affinity" and that this property is "insensitive to the distribution of the dataset": a placement solved from 1,000 Pile tokens reproduces on C4, Dolma, and Yelp [326][779]. In distributed expert parallelism this cuts "up to 67 % of tokens' cross-GPU routing latency" and yields "up to 2.2x improvement in inference throughput" [326]. The analogue on this single-host two-GPU rig is a retention *prior*: if expert *e* was activated at layer *k*, its affinity partner at layer *k+1* should resist eviction from the 68 GB store even when its own recent access count is low. HybriMoE's impact-driven inter-layer prefetching already exploits this, predicting activations "for the next three layers by reusing the gating information" and achieving 1.33× prefill / 1.70× decode speedup [325]. ExpertFlow reports 92 % cache hit at CS = 16 with its predictive cache, versus LRU's 58.37 % at the same batch size [504][1054]. CoX-MoE's "expert-aware stratification" achieves "an expert hit ratio approximately 40% higher than random selection," translating to "a throughput improvement of up to 1.47–1.50×" [505]. For Qwen4's 512 experts / top-10, ExFlow's rule that 3,000 tokens suffice for a MoE-64 model suggests a warm-up of ~3 K tokens captures the affinity graph, after which the store's eviction policy can weight inter-layer co-activation alongside MRS. The constraint on this rig: any transfer triggered by an affinity miss must use the 5080's Gen5 ×16 link, never the 4060 Ti's chipset ×4 path, because the latter caps at single-digit GB/s and would stall the pipeline.

### Fine-grained gate / up / down transfer on three CUDA streams

PreScope decomposes each expert into its three linear weight matrices (gate_proj, up_proj, down_proj) and moves them on "three independent CUDA streams" concurrently, achieving "deep computation I/O overlap while using a fixed set of cache regions to guarantee correctness" [506][1734]. The gain over synchronous whole-expert transfer is stark: "Pytorch's coarse-grained operations are over 70% slower than AsyncIO's fine-grained approach, leading to a sharp drop in PCIe utilization" [506]. PreScope's end-to-end throughput improvement reaches 141 % over Klotski and 70.8 % over HybriMoE, with decoding latency cut 42.1–74.6 % [506]. Strata's existing pool already separates gate/up (which have no data dependency between them) from down in its MMQ phases—expert work breaks down as "MMQ gate/up 13.5 + down 7.5" per window [1]—so splitting the H2D copy at exactly that granularity matches the compute schedule without restructuring kernels. On the 5080's Gen5 ×16 at 913 GB/s aggregate read bandwidth [1], a single 10.27 MB expert transfer takes ~11 µs; three 3.4 MB sub-transfers on separate streams overlap with the 140 µs CPU pool time per layer and the 72.5 µs GPU work running beside it [1], making the transfer effectively free **[Setup check: The 5080's GDDR7 memory bandwidth is 960 GB/s, but its Gen5 ×16 PCIe transfer path is around 58 GB/s; a 10.27 MB PCIe transfer takes roughly 180 µs, not 11 µs.]** **[Consistency check: contradicts "The 5080 runs at PCIe Gen5 ×16 (57.8 GB/s H2D) directly off the CPU root complex; the 4060 Ti runs at Gen4 ×4 through..." elsewhere in this report, which the evidence supports; Replace the 913 GB/s PCIe-transfer assumption with 57.8 GB/s for H2D over the 5080's Gen5 ×16 link; a 10.27 MB H2D transfer is about 178 µs, not ~11 µs (913 GB/s is GPU memory bandwidth, not PCIe H2D).]**. On the 4060 Ti's chipset ×4 path the same transfer is roughly 9× slower, so this technique's benefit concentrates on the 5080's 32-layer span. The KTransformers paper confirms the broader principle: expert loading "dominates the total inference time, consuming approximately 85.5% on the RTX 4090" in offloading mode [1056 context via 502], and Fiddler notes "the time required to copy activation from the GPU to the CPU is negligible, accounting for less than 1% of the total latency" while weight transfer is the bottleneck [502]. Three-stream gate/up/down splitting attacks exactly that bottleneck without changing any arithmetic.

### GPU-overhang context on this rig

The 17.9 ms decode window contains 3.16 ms of exposed CPU flag-wait (16 %), the per-layer CPU pool runs 140 µs with the GPU working beside it for only 72.5 µs (52 % utilization), and GEMMs pull roughly 500 GB/s of the 913 GB/s ceiling [1]. The 0.44 ms of PCIe-group movement per window (expert copies counted at "waiting for expert copies 3.9 %" of window time) sits inside the 187–222 µs GPU phase gap per layer [1]. All four policy changes above act on this gap: exact-size slots raise hit rate so fewer copies are needed; MRS and affinity prioritize the experts whose copies *would* fill the gap; three-stream splitting fills the gap with overlapped transfers. The losslessness gate for each arm is the user's existing exact7 repeat test before any adoption.

## Tier 3: Prefill / prompt path — avoid redundant expert traffic, overlap streaming, and price already-written patches

### The bottleneck: chunked MoE prefill re-walks the expert pool per chunk

Strata's prompt path reads experts from the file tier (or RAM arena) in chunks. The Layered Prefill paper quantifies the core waste: "chunked prefill incurs substantial overhead in Mixture-of-Experts (MoE) models: redundant expert weight loads increase memory traffic by up to 39% and inflate energy consumption" [356][1596]. On this rig, a 97K-token DeepSeek prompt reads at 947 tokens/s over 102 s [user_setup], while the 20K-token Qwen prompt completes in ~5 s [user_setup]; the gap is not compute but repeated expert-pool traversal per chunk. The profile-pack's prompt speeds (pp16k 3,963.2; pp64k 4,567.7 tok/s) show throughput climbing with chunk size, confirming that per-chunk overhead dominates [1345]. The Qwen profile shows "expert work 42 % = MMQ gate/up 13.5 + down 7.5 (≈1.4 TFLOPS: ~160 rows per expert per 8192-chunk = underfilled) + the per-expert group gather 9.9 … + waiting for expert copies 3.9 %" [1], so at 8192-token chunks the GPU's MMQ is only ~160 rows/expert (underfilled) and the dequant-gather phase is the largest single item.

Strata's chunk cap is 8192 tokens (the DeepSeek config uses `prompt chunk 8192` [user_setup]); Basalt's fixtures (16,676 = 16,384 + 292 and 66,617 = 4 × 16,384 + 1,081) show that "a short leftover chunk still makes a full pass over the experts with little compute to hide it, ~0.5–0.7 s, about half the 16K gap" [13]. Raising the chunk from 8192 to 16384 measured −13.4 % TTFT at 32K and −13.6 % at 120K [1342], but the user's DeepSeek config keeps 8192 for the two-card layer split [9].

### Ostinato's resident-set / two-path policy (lossless by construction)

Ostinato's key insight is directly applicable: "a short prefill touches too many distinct experts to upload, yet sends 84% of its expert activations (routes) to a stable set of experts that fits in GPU memory" [48][1599]. Its two-path policy: "Short prefills split their routes, leaving fewer than one of a token's six routed experts per layer to the CPU; long prefills upload each distinct cold expert once" [48][1599]. Against llama.cpp and KTransformers it "cuts the median wait after a tool output by 22-55% and finishes sessions 1.4-2.5× sooner" on DeepSeek-V4-Flash across four RTX 4090D GPUs [48]. The mechanism is lossless because it changes *which device computes each expert* (CPU vs GPU), not *which expert runs*: routing decisions and per-token summation order are untouched **[Check: reasoning: Changing CPU vs GPU execution does not by itself guarantee bit-identical logits. If the two backends use different GEMM accumulation order, precision, or fused dequant kernels, the output can differ. The report's own exact7/NLL gates elsewhere imply that bit equality must be measured, not assumed. (This mechanism can be output-exact only if Strata's CPU and CUDA expert paths are meas...]**.

On this rig, the 5080's 16 GB GDDR7 holds ~4,600 expert slots for Qwen [user_setup]; the stable 84 % set concept maps to the VRAM-resident pool already maintained. The untried gain is *not re-evicting those cached experts* between prompt chunks — currently, a chunk that activates a cold expert can displace a hot one, forcing a re-fetch on the next chunk. Ostinato's "resident in every forward pass" invariant (no eviction during prefill if the stable set fits) would be exact and avoid the 39 % redundant-traffic penalty [356].

### Layered prefill within a chunk — and the STRATA_PREFILL_LAYER_MAJOR trap

Layered Prefill's alternative: "vertically partitioning the model into contiguous layer groups and interleaving prefill and decode across the groups" so "each layer is traversed exactly once" [356][1596], lowering TTFT by up to 70 % and end-to-end latency by 41 % [356]. KTransformers' layerwise prefill implements a similar idea: "For each chunk and each MoE layer, prepare full layer working weights — The layer needs to move CPU-side working weights to GPU (primarily over PCIe)" with a "per-expert three-stage pipeline inside each layer: Stage A: weight format conversion; Stage B: PCIe transfer; Stage C: Marlin repack postprocess" [592]. Its "net effect: much lower DRAM bandwidth pressure, with bottleneck concentrating more on PCIe and GPU compute" [592].

**Critical caveat for this rig:** v0.2.7 turned on `STRATA_PREFILL_LAYER_MAJOR` "on for a 2-card CUDA layer split; other summation order" [12]. This changes the per-token summation order (layer-major vs token-major accumulation) and is therefore *not bit-exact*. It is "pinned off in the port; layer-major added as a gate + TTFT arm" [12]. The `PREFILL_V2` kernels on the served P021m build "FAIL the 36-row NLL check" (NLL +0.143 above reference, bound 0.086) [12], though the ported v2 is "exact (bit-identical to v2 off; NLL −0.024 PASS)" [12] **[Version check: `PREFILL_V2` - not in the code at your version; only your own files name it (your own build's setting?) (Other build/port kernel option; absent from v0.2.6 code.); not an option of Niko1221/Strata v0.2.6 as far as the code shows]**. Any layered-prefill idea must preserve per-token summation order exactly — the same fix KTransformers achieves by keeping the *per-layer* traversal within a chunk (each layer once) without reordering the accumulation across tokens within that layer.

## Tier 4: Speculative-decoding verification and MoE-aware expert scheduling during SD

The one untried axis of Strata's speculative stack is *verification order*—how the target model's accept/reject rule traverses a multi-draft tree. Strata's tree drafting was rejected at −10% under naive top-down tree verification, and no optimal-order verifier (GBV, Traversal, OT-based) has been re-tried on this engine [1064][1067]. Everything below is provably output-exact: the target distribution is unchanged regardless of verification order, so the losslessness constraint holds by construction.

### Verification-order algorithms not yet priced

**Greedy Block Verification (GBV)** proves that block verification is optimal even over verifiers that use off-path probabilities, improving walltime >15% over standard BV and >30% over SOTA multi-path on Llama-3 70B; recommended settings are L=8, K=3, with diminishing returns past K=3 (+15% K=1→2, +4.4% 2→3, +2.5% 3→4) [1064][1205]. A critical caveat for Qwen-family targets: for Qwen-3, K=1 is best because the draft step dominates 70% of the round, so wider multi-path verification cannot amortize its expert-expansion cost [1064][1205]. Strata's MTP drafter commits 3.65 tokens per verify window at 72.9% acceptance (v0.2.13 gate, 2026-11-10) [1095], meaning the draft is already a large share of the round—making the K=1 caveat directly relevant here.

**Traversal Verification** (NeurIPS 2025) performs leaf-to-root post-order DFS on sequence-level joint probabilities, proving the output distribution is identical to the target's; it gains +2.2–5.7% average acceptance length and +1.7–4.8% tok/s over token-level top-down tree verification, with the advantage growing at tree depth [1067][1069][1198]. The 2026 follow-up (NDE, arXiv 2602.16994) confirms "Traversal Verification dominates consistently" over OT-based verifiers across model families, tasks, and sampling regimes, though a neural MLP selector can lift SpecInfer-NDE ~5% above Traversal in certain regimes [1057][1059][1062][1197].

**Global Resolution** (Thomas & Pal, ICLR 2026) gives the first *efficient* exact-OT algorithm for n≥2 i.i.d. drafts, reducing the exponentially large OTLP to a convex problem in ≤|𝒱| variables—10,000× faster than generic solvers—while keeping L1 deviation from the target ≤15τ [1331][1310][1322]. It achieves >90% acceptance at <100 ms/token overhead where generic LP solvers reach only 84%, and ~2× walltime inside SpecTr on 27B/2B and 70B/8B pairs [1331].

**SpecTr-GBV** (EMNLP 2026 main.1340) unifies multi-draft and greedy block verification as a single OT over draft/target *blocks*, proving the optimal expected acceptance length within i.i.d. drafting; verification complexity is O(|𝒱|) per step versus O(|𝒱| log K) for SpecTr, with >50% lower verification overhead [1293][1335]. In the 6.7B/1.3B case it yields +11.6% average block efficiency and +14.3% average speedup over SD [1335].

### MoE-aware verification capacity

On this rig the MoE verification cost is the binding constraint, not the token count. The "Why SD Works Better Than Predicted" paper (NeurIPS 2026) shows that for fine-grained MoEs like Qwen3-30B (512 experts, k=8), at batch 1 MoE kernels take only 33% of forward GPU time despite holding 66.7% of weights, because L2 absorbs repeated reads of co-routed experts: the hit rate rises from 5.72% autoregressive to 27.79% under SD [1014]. ## Tier 5: CUDA-graph launch overhead and Qwen4-Flash-specific switches pinned off in the port

### CUDA-graph capture for the decode window

The single largest untried GPU-side mechanism in this port is capturing the decode window as a CUDA graph. The window's structure is already known: 2,337 kernel boundaries per traced window, with the GPU's total idle gaps at only 0.24 ms per window and PDL recovering at best 0.14 µs per boundary (2,337 × 0.14 µs ≈ 0.33 ms ≈ 1.8% of a 19.9 ms window) [3]. The PDL microbenchmark confirms the ceiling: with real work (336 blocks × 512 iterations) PDL saves only 0.14 µs per boundary, and the early-trigger variant actually slows the kernel to 47.3 µs because waiting blocks occupy SMs [4]. By contrast, the CPU-side flag-wait is 3.16 ms of a 17.9 ms traced window = 16%, and the per-layer dispatch before the workers start is 10.7 µs of serial host work (plan 1.0 + activation quantize 6.9 + jobs 2.8 µs per layer; 0.51 ms/window total) [1]. The sync audit adds that the drafting phase runs 2.34 graph launches + 2.34 stream syncs per round, with GPU busy only 1.113 of 1.354 ms (idle 0.24 ms) [3].

KTransformers demonstrates the ceiling of the idea: "CUDA Graph integration captures the hybrid CPU/GPU execution as continuous graphs. To make captures robust, KTransformers uses asynchronous task scheduling so that CPU tasks and data transfers do not create 'breakpoints' in the captured graph. Capturing the workload this way reduces GPU kernel-launch overhead from over 20% to nearly zero" [192]. The SOSP-25 paper reports KTransformers achieving "speedups ranging from 2.42× to 4.09× over Fiddler and 1.25× to 1.76× over Llama.cpp" in the decode phase for full-precision models [193]. llama.cpp PR #26802 captures CUDA graphs to cut per-launch overhead, noting it "matters most exactly when the model is small enough that launch overhead is a real fraction of the work — MoE decode, in other words. Graph capture cannot survive a mid-capture stream synchronisation" **[Citation check: its citation pointed to no source of this research and was taken out; this statement has no source]**. A 32-layer Llama decode step launches ~400 CUDA kernels; at 7 µs each, that is 2.8 ms of pure scheduling cost **[Citation check: its citation pointed to no source of this research and was taken out; this statement has no source]**. On the user's rig, with 48 layers and expert GEMMs pulling ~500 GB/s of the 913 GB/s GPU bandwidth ceiling [4], launch overhead per kernel is a smaller fraction than on a dense 7B model, so the NVIDIA blog's 1.2× peak for Llama-7B on H100 [4050] understates what the 48-layer MoE graph would save in absolute µs but overstates it relative to per-kernel compute time.

The data-dependent-shape obstacle is real: "Adaptive speculative decoding changes the active batch size B and draft length d from one decode step to the next, whereas a CUDA Graph replays a fixed launch configuration" **[Citation check: its citation pointed to no source of this research and was taken out; this statement has no source]**. PolyGraph resolves this for Triton kernels by "captur[ing] one maximum-grid graph and writ[ing] the active shape to GPU memory before each replay," transferring only 28 bytes per update **[Citation check: its citation pointed to no source of this research and was taken out; this statement has no source]**. A hybrid JIT-CUDA Graph runtime "overlap[s] JIT-executed dynamic operations with deterministic CUDA Graph replay to reduce kernel launch overhead and latency variance during autoregressive decoding" **[Citation check: its citation pointed to no source of this research and was taken out; this statement has no source]**. KTransformers' asynchronous task scheduling is the structural answer to the flag-wait problem: if CPU expert results arrive on a different stream, they do not break the graph, and the 27 in-window syncs (the CPU pool's flag waits, which are needed) become graph nodes rather than host round-trips [3]. On this two-card rig the 5080's free Gen5 ×16 link (57.8 GB/s H2D, 58.0 GB/s D2H) [3906] can carry the async transfers that keep the graph intact, unlike the chipset ×4 (6.4 GB/s H2D, 6.8 GB/s D2H) [3906] behind the 4060 Ti.

### The GDN-kernel losslessness boundary

Qwen3.8-Flash-Next carries 36 GDN layers (one GDN:QSA ratio of 3:1 across 48 layers) [1879][1892]. For Qwen4, every rejected MTP draft must roll back the GDN recurrent state at each of those 36 layers, making the state-rollback mechanism (STRATA_PIPELINE_SNAP_OVERLAP in Tier 0) the single most Qwen4-relevant item.

No fast GDN kernel is currently usable losslessly here. FlashQLA operates in BF16: "FlashQLA BF16 inputs (block_DV 64/32) | 3.7e-3 | 2.3e-3 | 1.09 ms kernel; 6.02 ms with the FP32→BF16 cast" [4]. The measured error (3.7e-3 vs the FP64 reference at 9e-16) means "FlashQLA is ~1,600× less accurate (BF16) = not allowed; with conversions it is not faster than today; an FP32-accurate tensor-core variant (3xTF32) would cost several times its BF16 time ≈ no gain" [4]. The Veitner similarity transform (N = GMG⁻¹ where G = diag(exp(g^cum_1), …, exp(g^cum_C))) accelerates the WY solve by 1.15× [2433][2399], but the chunked-vs-recurrent gap remains: "the chunked kernel slices the sequence into fixed-size chunks, computes each chunk in matrix form, and carries the state across chunk boundaries; the recurrent kernel walks the sequence token by token. The two compute the same function in a *different order*, so they do not agree bit for bit" [2033]. GDN chunked prefill was dropped: "recurrence = 7.6% of prompt GPU time, a precision-preserving ceiling of ~0–2% of prompt time ≈ < 0.1% of your total time" [4]. No batch-invariant fast GDN attention kernel exists yet.

### The drafter profile gap

The drafting phase (2.34 graph launches + 2.34 syncs per round) consumes 1.354 ms of wall time per round with the GPU busy only 1.113 ms [3], and the timing-log decomposition puts drafting at 2.29 ms per token (0.94 fixed + 0.39 per step) [10].
