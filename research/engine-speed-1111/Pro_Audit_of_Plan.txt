**Yes—I’d use this as the working plan, with a few targeted revisions.** The strongest parts are separating fixed-work timing from free-running generation, testing adaptation and rejected drafts explicitly, and using replay to decide which larger changes deserve implementation.

## 1. Keep the testing rule—and make “fixed work” precise

This is the most important improvement in the plan.

**Generating the same number of output tokens is not necessarily fixed work.** Different tokens, acceptance lengths and cache histories can produce different expert traffic.

I would maintain two separate measurements:

| Measurement | Hold constant | What it establishes |
|---|---|---|
| **Fixed-work replay** | Token/input sequence, context positions, window widths and initial cache state. For kernel comparisons, also hold execution placement constant. | Whether the implementation performs the same work faster. |
| **Free-running generation** | Workloads, sampling settings, startup/warm-up procedure and evaluation rules. | Whether the complete serving system becomes faster, including acceptance and adaptation effects. |

For **cache-policy experiments**, replay the same demand and initial state but allow the candidate to make its own placement decisions. Freezing placement there would remove the mechanism being tested.

There is also one concrete instrumentation gap: **your profile says `STRATA_SPEC_DEPTH=1` reports positions 1–5, while you serve with spec 7.** Confirm the current implementation and extend it through depths 6–7 before calling the coverage complete. The down-projection formats are already known—**39 IQ4_NL layers and nine Q2_0 layers**—so the new measurement is their association with misses and elapsed time. [Source: PROFILE-PACK, sections 2 and 6](https://raw.githubusercontent.com/KarlGrier/local-ai-setup/main/research/engine-speed-1111/PROFILE-PACK.md)

For correctness, distinguish two tests:

- **Forced-path state tests:** exercise rejection at each depth, full acceptance and the bonus-token path; compare subsequent state/logits against a reference consuming the same committed sequence. Include admission, eviction and in-flight copy cases.
- **Distribution tests:** use the real acceptance logic and normal random draws. Forced rejection is useful for testing rollback, but cannot establish unbiased sampling.

That makes the new rule materially stronger than repeating `exact7` with adaptation disabled.

## 3. Make Phase B’s build threshold about throughput

The replay harness is probably the most valuable larger investment in this plan.

I would change:

> “Build only those worth about +3 points or more.”

to:

> **“For substantial new patches, require roughly 3% predicted end-to-end throughput improvement after movement and scheduling costs; report GPU hit-share changes as supporting evidence.”**

If Opus already meant throughput percentage, just make that explicit.

Three percentage points of GPU hit share do not have a fixed value. An expert serving several speculative columns contributes several routed-entry hits but may require only one CPU weight read. Moving work between the main GPU and helper can also improve—or worsen—completion time without changing their combined hit share.

The proposed routing tuple is a good start. To evaluate all eight policies, it also needs:

- **Request/window IDs, context length, width, accepted prefix and draft origin**—MTP versus suffix lookup.
- **Expert byte size/format, initial residency and per-layer budgets.**
- **Admission/eviction events and timing intervals** for CPU work, copies and helper completion.
- **Prompt boundaries and cache borrowing/reseeding events.**
- **KV residency/access information** if runtime KV/expert allocation stays in scope.

Two particularly important charges:

**Admitting a CPU-served miss requires a new copy.** Today’s `ADAPT_FETCH` admission reuses an expert already transferred to the main GPU. An adaptive helper likewise adds traffic over its slower link. These cannot be priced as free cache improvements. Your PR makes the already-fetched nature of current admission explicit. [GitHub](https://github.com/Niko1221/Strata/pull/5813)

And replay must be **causal**: a policy can use observed history, not future requests. A hindsight placement is useful as an explicitly labelled upper bound. Let each simulated policy evolve its own cache state rather than inheriting the baseline’s eviction decisions.

## 5. Turn the block-verification parenthetical into a hard prerequisite

**I should tighten my earlier recommendation here:** I assigned a potential gain before establishing the actual proposal law used by your draft path.

For a deterministic argmax or suffix-lookup proposal, the proposal distribution is **one-hot**: \(q(y)=1\) for the chosen token. The drafter’s softmax confidence is not its sampling probability in that case.

For an unchanged, fixed deterministic chain, ordinary exact token verification already achieves the target probability of retaining each prefix. **Block verification cannot increase accepted-prefix length merely by changing the verification algorithm.** This follows by specializing the standard acceptance rule to a point-mass proposal. [proceedings.iclr.cc](https://proceedings.iclr.cc/paper_files/paper/2025/file/3e710b42b1a9ed898f607ec0f4fcc971-Paper-Conference.pdf)

Therefore:

- **Actually sampled MTP proposals:** investigate Block Verification, with the correct probabilities and adaptive stopping treatment.
- **Deterministic proposals:** expect **zero acceptance improvement for the same chain**; any implementation-overhead improvement is a separate claim.

For suffix trees, “one-hot exact rule” also needs a precise implementation. A straightforward exact approach samples **once from the target at the current node**, follows the matching child if present, and otherwise emits that sampled token and ends traversal. Independently accepting multiple branches against the unchanged target distribution would not implement that rule.

Opus already identified the right question. I would resolve it during the desk checks, before reserving a patching gap.

## 6. Keep Phase D exploratory, with fuller cost models

All three desk projects belong there.

**Two-group overlap:** the “fixed part below two-thirds” threshold is a preliminary heuristic. Window width alone does not determine CPU time: distinct misses, multiplicity, format, cache state and concurrent copies matter. Your GPU-reach counter is host-observed waiting, not pure GPU execution. The model needs to subtract duplicated weight reads, lost cross-token reuse, additional launches, state handling and pipeline fill/drain costs from the proposed overlap.

**Exclusive residency:** start with genuinely fixed helper experts. Keep its value classified as **Qwen4 capacity/headroom**, with little current decode benefit. Dynamic main-cache entries need a correct eviction/refetch mechanism before their host backing can disappear.

**Compression:** sampling actual packed experts is the right first step. Add decompression throughput and scratch traffic to the report. Decompressing into a RAM buffer and then reading that buffer for the matvec can erase the original bandwidth saving. Separate “helps the larger model fit” from “makes today’s model faster.”
